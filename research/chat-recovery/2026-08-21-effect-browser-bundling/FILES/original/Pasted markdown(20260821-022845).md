# Effect browser bundling: findings and recommendation

## Decision

Use **Effect 3.22.1** for the production application, with the matching stable platform packages—`@effect/platform@0.97.1` and `@effect/platform-browser@0.77.1`. Keep **Effect 4.0.0-rc.111** in a pinned comparison branch until it reaches GA and the browser fixtures are rerun. The v4 package is still a release candidate and its HTTP APIs are currently exposed through `effect/unstable/*`, so its present bundle numbers should not drive a production migration.

The key architectural recommendation is:

> **Effect should begin at the interactive-player boundary. Static acquisition, atlas, reference, FAQ, announcement, and source pages should not import the Effect runtime at all.**

That is not because Effect fails to tree-shake. It tree-shakes well. It is because an **executable Effect runtime still has a meaningful floor**: the current official runnable `Effect.succeed(...).pipe(Effect.runFork)` fixture is 30.25 kB gzip, while executable Schema, Stream, and HttpClient fixtures are larger. Those are reasonable lazy-player costs, but poor baseline costs for otherwise static pages.

Vite 8 is now Rolldown- and Oxc-based rather than Rollup- and esbuild-based. It became stable on March 12, 2026; current Vite configuration should use `build.rolldownOptions`, while `build.rollupOptions` is only a deprecated compatibility alias. ([vitejs](https://vite.dev/blog/announcing-vite8 "https://vite.dev/blog/announcing-vite8")) ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

## Measurement status and methodology

All figures below concern **emitted JavaScript**, not npm tarball size, unpacked installation size, type declarations, tests, source files, or package-manager metadata.

There are three evidence grades:

- **Measured:** exact output from the Effect project’s own bundle tooling.
- **Calibrated:** minified and Brotli ranges derived from exact same-tool measurements where only the current gzip number is retained.
- **Planning estimate:** a budget range for a fixture that does not exist in the official corpus.

The current Effect harness:

- emits ESM through Rollup;
- resolves the built Effect package output;
- replaces `process.env.NODE_ENV` with `"production"`;
- lowers TypeScript with esbuild and enables tree-shaking;
- minifies with Terser compression and mangling;
- measures gzip level 9;
- currently targets `node20`, not Vite’s browser target.

Therefore, its current gzip results are excellent **comparative evidence**, but they are not mislabeled here as Vite 8 browser-target measurements. Browser transpilation, Oxc-versus-Terser differences, chunk boundaries, and package-version differences can move the final numbers.

The stable v3 branch does not retain a comparable official bundle-size CI job, and this environment could not reach npm to create a clean Vite installation. I therefore do **not** assign fabricated stable-v3 browser numbers. The production repository should run the supplied fixture discipline before locking its final budgets.

### Another important methodology difference

The Effect harness streams all emitted Rollup chunks through one gzip stream. That is appropriate for its regression comparison, but real browsers receive chunks as separate HTTP responses. For deployment budgets, compress **each emitted file independently and sum the results**; concatenating chunks first produces slightly optimistic compression.

All kB figures below use decimal kB, matching the Effect report.

### How to interpret the Layer estimate

A small `Context` service and `Layer.succeed` should remain close to the basic Effect runtime. Layer itself should not be treated as an automatic 20–40 kB increase.

The larger jumps come from the **service’s implementation and imported feature family**:

- the current Cache fixture is 31.56 kB gzip;
- the Config fixture, which also pulls Schema functionality, is 78.41 kB gzip.

Consequently, “uses Layer” is not a useful bundle-size category by itself. “Uses Layer to provide Config + Schema + HttpClient” is.

### Proposed question-player fixture

The 58–72 kB gzip planning range assumes:

- `effect/Effect`;
- `effect/Schema`;
- `effect/Ref`;
- `effect/Context`;
- `effect/Layer`;
- question-set decoding;
- commit-before-reveal state transitions;
- deterministic answer scoring;
- a small service for progress persistence;
- approximately 3–10 kB gzip of application and DOM-controller code.

It excludes:

- `effect/Stream`;
- `@effect/platform/HttpClient`;
- Effect Config;
- offline-pack download orchestration;
- image assets;
- question content;
- IndexedDB helper libraries;
- a UI framework.

Because the Effect and Schema graphs overlap, the estimate is **not** `30.25 + 55.23`; compressed feature costs are not additive.

The broad barrel pulled `msgpackr` into the graph because that dependency had genuine module-scope behavior and lacked metadata allowing the bundler to discard it. The equivalent deep public subpath avoided that cost.

This produces two practical conclusions:

1. Effect’s own `sideEffects` metadata works.
2. It cannot make a transitive third-party module pure when that module is not pure.

# ESM, tree-shaking, `sideEffects`, and imports

## Package shape

Stable Effect v3 is ESM-first and publishes public module subpaths. Its source export map exposes the root and `./*` public modules while blocking internal paths.

The v3 packaging process generates:

- ESM and CommonJS export conditions;
- per-subpath proxy package metadata;
- empty `sideEffects` arrays for those public subpaths;
- root package metadata that defaults to no side-effectful files.

The v4 package directly declares `sideEffects: []` and exposes its public module set through package exports.

## Recommended import discipline

Use public subpaths:

```ts
import * as Effect from "effect/Effect"
import * as Schema from "effect/Schema"
import * as Ref from "effect/Ref"
import * as Context from "effect/Context"
import * as Layer from "effect/Layer"
```

For stable v3 browser HTTP:

```ts
import * as HttpClient from "@effect/platform/HttpClient"
import * as FetchHttpClient from "@effect/platform/FetchHttpClient"
```

Avoid in browser entrypoints:

```ts
import * as EffectAll from "effect"
import * as Encoding from "effect/unstable/encoding"
```

A namespace import from a **focused subpath** is fine. Effect’s official fixtures themselves use `import * as Effect from "effect/Effect"` and still tree-shake. The meaningful distinction is:

- focused public subpath versus broad barrel;
- actually executed feature versus dead definition;
- pure module versus module with top-level behavior.

Named imports can improve readability, but changing:

```ts
import * as Effect from "effect/Effect"
```

to:

```ts
import { succeed, runFork } from "effect/Effect"
```

should not be treated as the primary optimization.

Also use `import type` consistently so model and service types do not create accidental runtime edges.

# Vite 8 production settings

Vite 8 uses Rolldown for bundling and Oxc for transformation and default client minification. The old `build.rollupOptions` name is deprecated; use `build.rolldownOptions` only where direct bundler configuration is actually needed. ([vitejs](https://vite.dev/blog/announcing-vite8 "https://vite.dev/blog/announcing-vite8")) ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

A suitable starting configuration is:

```ts
import { defineConfig } from "vite"
import { resolve } from "node:path"

export default defineConfig({
  appType: "mpa",

  input: {
    home: resolve("index.html"),
    atlas: resolve("atlas/index.html"),
    reference: resolve("reference/index.html"),
    player: resolve("study/index.html")
  },

  resolve: {
    dedupe: [
      "effect",
      "@effect/platform",
      "@effect/platform-browser"
    ]
  },

  build: {
    target: "baseline-widely-available",
    manifest: true,

    // Use false when maps are unnecessary. With "hidden", upload them
    // privately and remove them from the deployable static directory.
    sourcemap: "hidden",

    // Default in Vite 8. Benchmark "terser" separately before changing.
    minify: "oxc",

    // A custom budget script should calculate both gzip and Brotli.
    reportCompressedSize: false
  }
})
```

Vite recommends the top-level `input` option in Vite 8 so entries are shared by development and build. It also offers `resolve.dedupe` specifically to force listed dependencies to resolve to one root copy. ([vitejs](https://vite.dev/config/shared-options.html "https://vite.dev/config/shared-options.html"))

## Browser target

Vite 8’s default `baseline-widely-available` target is fixed to the January 1, 2026 baseline:

- Chrome 111;
- Edge 111;
- Firefox 114;
- Safari 16.4;
- iOS 16.4. ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

Use that default unless the product explicitly promises older devices. If older iPhones or embedded webviews are in scope, define the target from the actual support contract and test the resulting output. Vite transpiles syntax; it does not automatically provide every missing browser API needed by IndexedDB, Cache Storage, service workers, `fetch`, or other application code.

## Minification

Vite 8 defaults to Oxc for client builds. Its documentation describes Oxc as much faster than Terser but approximately 0.5–2% worse in compression. Terser remains available as an explicit option and separate dependency. ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

For this project:

1. Use Oxc during normal development and initial CI.
2. Produce a second release-candidate build with Terser.
3. Compare **independently compressed gzip and Brotli closures**, not only uncompressed output.
4. Keep Terser only if the transfer reduction is meaningful enough to justify the slower build and extra tooling dependency.

Because Effect’s official figures use Terser, the Terser variant gives the cleaner comparison with those figures.

## Source maps

Vite defaults production source maps to `false`. `"hidden"` emits separate map files but omits source-map references from the JavaScript. ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

Recommended policy:

- local and staging: `"hidden"`;
- production with an error-ingestion service: upload privately, then delete maps from `dist`;
- production without such a service: `false`;
- never include `.map` files in the service-worker precache or JavaScript budgets.

## Gzip and Brotli

Vite’s built-in `reportCompressedSize` reports gzip only. It does not constitute a Brotli budget. ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

The CI size tool should calculate:

```ts
gzipSync(code, { level: 9 })
brotliCompressSync(code, {
  params: {
    [constants.BROTLI_PARAM_QUALITY]: 11
  }
})
```

Use the same levels for every baseline so changes remain comparable.

# Chunking architecture

## Recommended delivery graph

```text
Static acquisition/reference HTML
├── CSS
└── 0–6 kB gzip optional progressive enhancement
    └── no Effect imports

study/index.html
├── small page/controller entry
└── player-runtime.[hash].js
    ├── Effect
    ├── Schema
    ├── Ref
    ├── Context / Layer
    └── question-player domain code

Lazy optional boundaries
├── offline-manager.[hash].js
├── network-content-update.[hash].js
│   └── @effect/platform HttpClient
├── reporting-export.[hash].js
└── stream-processing.[hash].js
    └── effect/Stream
```

## Static pages

The acquisition, announcement, FAQ, atlas, reference, and source pages should preferably be separate HTML entries with:

- semantic HTML;
- normal links and forms;
- CSS;
- no JavaScript where not necessary;
- tiny page-local progressive enhancement where necessary.

Do not put a global `site.ts` on every page if that file imports an application container which imports Effect.

Validate immutable content at **build time**, then emit static HTML or compact JSON. The atlas should not ship Schema simply to revalidate content that the build has already validated.

## Player boundary

A dedicated `/study/` HTML entry is cleaner than loading the player from the homepage. It naturally prevents Vite from preloading player dependencies on static pages.

Where an inline transition is required, preserve a hard dynamic boundary:

```ts
const startButton = document.querySelector<HTMLButtonElement>(
  "[data-start-player]"
)

startButton?.addEventListener("click", async () => {
  const { startPlayer } = await import("./player/bootstrap")
  await startPlayer()
})
```

Vite splits lazy imports into separate chunks. When a dynamic import is invoked, Vite rewrites it so common dependencies can be requested in parallel with the async chunk rather than after another network round trip. It also generates module-preload directives for entry chunks and their direct imports. ([vitejs](https://vite.dev/guide/features "https://vite.dev/guide/features"))

Do not add a manual `effect-vendor` chunk merely for neat filenames. A shared vendor chunk is useful only if it improves real route caching. If every HTML entry references it, the split defeats the primary requirement and causes static pages to download Effect.

Start with natural entry and dynamic-import boundaries; add manual chunk rules only after inspecting the emitted manifest.

# `modulepreload` discipline

Vite’s `build.modulePreload` defaults to `{ polyfill: true }`. The polyfill is injected into each HTML entry’s proxy module, and Vite computes dependency preload lists for both HTML entries and dynamic imports. ([vitejs](https://vite.dev/config/build-options "https://vite.dev/config/build-options"))

For this application:

- HTML pages with no module entry receive no reason to load the player.
- The player HTML entry may preload its static runtime dependencies.
- A dynamic player import does not need to preload Effect before the import is invoked.
- Keep the polyfill default initially because the Vite browser baseline includes Firefox 114; disable it only after an explicit compatibility test.
- Do not add `<link rel="modulepreload">` for the player to acquisition or atlas HTML.
- Do not automatically prefetch the player during idle time on a low-bandwidth site.
- Intent-based prefetching may be considered after focus, pointer hover, or an explicit “prepare offline” action, with Save-Data and connection conditions respected.

# Duplicate Effect copies

Duplicate copies can arise from:

- incompatible `effect` peer ranges;
- mismatched independently versioned v3 platform packages;
- linked workspace packages;
- npm/pnpm overrides or aliases;
- importing both stable v3 and v4-era packages into one graph.

Stable `@effect/platform-browser@0.77.1` peers against the matching stable Effect and platform lines, so version alignment should be deliberate.

Use all four controls:

```ts
resolve: {
  dedupe: [
    "effect",
    "@effect/platform",
    "@effect/platform-browser"
  ]
}
```

```json
{
  "pnpm": {
    "overrides": {
      "effect": "3.22.1",
      "@effect/platform": "0.97.1",
      "@effect/platform-browser": "0.77.1"
    }
  }
}
```

Then enforce in CI:

```bash
pnpm why effect
pnpm why @effect/platform
pnpm why @effect/platform-browser
pnpm list effect @effect/platform @effect/platform-browser --depth Infinity
```

The CI check should fail if more than one resolved production version appears. Vite’s `resolve.dedupe` is a useful final resolver guard, but it should not replace a correct lockfile. ([vitejs](https://vite.dev/config/shared-options.html "https://vite.dev/config/shared-options.html"))

# Recommended performance budgets

These are transfer budgets for emitted JavaScript, not content, images, HTML, CSS, maps, or install footprint.

“Closure” means the entry plus every statically imported JavaScript file needed to execute it. Dynamic descendants are excluded until invoked.

| SurfaceTarget: minified / gzip / BrotliHard gateDesign implication |                          |                       |                                                                  |
| ------------------------------------------------------------------ | ------------------------ | --------------------- | ---------------------------------------------------------------- |
| **Initial acquisition/reference page**                             | ≤20 / **≤6** / ≤5.5 kB   | 40 / **12** / 10.5 kB | No Effect; ideally zero JS                                       |
| **Interactive-player lazy closure**                                | ≤220 / **≤70** / ≤63 kB  | 270 / **85** / 77 kB  | Effect + Schema + small Layer; no Stream or HttpClient initially |
| **Service worker**                                                 | ≤15 / **≤4** / ≤3.6 kB   | 30 / **8** / 7.2 kB   | Native service-worker APIs; no Effect runtime                    |
| **Offline manager, incremental lazy bytes**                        | ≤50 / **≤15** / ≤13.5 kB | 80 / **25** / 22.5 kB | Share already-loaded player core or remain native                |
| **Offline manager, direct cold entry**                             | ≤125 / **≤40** / ≤36 kB  | 160 / **50** / 45 kB  | If it imports Effect independently, the core runtime dominates   |

The player target provides roughly 15 kB gzip of headroom above the current executable Schema fixture. The hard gate remains below the current standalone v4 HttpClient fixture, intentionally forcing network acquisition into a separate optional boundary.

## Consequences of these budgets

- Importing HttpClient into the initial player graph is a budget violation.
- Importing Config + Schema into the initial graph is likely near the warning threshold.
- Stream should remain out unless the question-player behavior genuinely requires streaming or backpressure.
- The service worker should not run Effect.
- An offline manager implemented with Effect can meet the **incremental** budget only when the core runtime has already been loaded and cached.
- Reference pages must not share an eagerly imported application bootstrap with `/study/`.

# CI bundle discipline

Run two kinds of build.

## 1. Isolated fixture builds

Build each of the six fixtures independently. This answers:

> What is the complete cost of this feature if it is the only application entry?

Use separate exact dependency sets for:

- stable v3;
- pinned v4 RC comparison.

Keep identical:

- Vite major/minor;
- browser target;
- minifier;
- source-map setting;
- fixture behavior;
- compression levels.

Do not compare a v3 Terser build against a v4 Oxc build.

## 2. Integrated multi-page build

Build the actual route graph and calculate:

- acquisition static closure;
- atlas static closure;
- player static closure;
- each dynamic closure;
- incremental bytes after subtracting already-loaded shared chunks.

Generate `build.manifest: true`, then recursively follow each manifest entry’s `imports`. Follow `dynamicImports` only when measuring that optional feature.

For network-realistic values:

1. collect each distinct `.js` file in the closure;
2. read its emitted bytes;
3. gzip that file independently;
4. Brotli that file independently;
5. sum the independently compressed results;
6. exclude `.map` files;
7. fail against the relevant target and hard gate.

Store with every CI result:

- exact package versions;
- Vite version;
- browser target;
- minifier;
- gzip level;
- Brotli quality;
- manifest;
- per-file and closure totals.

This prevents a future report from silently comparing different targets or compression settings.

# Features responsible for meaningful size increases

The current evidence supports this ordering:

1. **Executing the Effect runtime:** approximately 30.25 kB gzip in the current RC fixture.
2. **Executable Schema decoding:** approximately 55.23 kB total gzip.
3. **Stream:** approximately 50.26 kB total gzip.
4. **Config combined with Schema:** approximately 78.41 kB total gzip.
5. **Fetch-backed HttpClient:** approximately 84.03 kB total gzip.
6. **Broad barrels with effectful transitive dependencies:** demonstrated +9.992 kB gzip over the equivalent focused import.

The main discipline is therefore not “avoid Effect abstractions.” It is:

> **Keep feature families out of closures that do not use them, and make route boundaries match product behavior.**

# Final architecture recommendation

Adopt this shape:

- **Static MPA shell:** Vite, semantic HTML, CSS, and minimal page-local TypeScript.
- **Production Effect line:** `effect@3.22.1` with matching platform packages.
- **Player runtime:** lazy or player-page-only chunk containing Effect, Schema, Ref, Context, and Layer.
- **Persistence:** IndexedDB adapter behind a small service, included with the player.
- **Offline worker:** native service-worker code, independent of Effect.
- **Offline-manager UI:** separate lazy boundary; no question engine imports.
- **Network content updates:** separate optional HttpClient boundary.
- **Stream:** excluded until a measured use case requires it.
- **v4:** exact-version comparison branch only; rerun the same browser fixtures at GA.

Under this discipline, Effect is compatible with a low-bandwidth mobile-first application. It is not compatible with placing a common Effect bootstrap on every static page. The correct target is a nearly JavaScript-free acquisition/reference surface and an approximately **60–70 kB gzip interactive-player closure**, with CI preventing optional Effect subsystems from leaking into that boundary.
