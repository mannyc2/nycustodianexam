# Launch pack authoring

The English launch pack has two deliberately different representations:

- `launch-v1.curated.mjs` is the human-reviewable editorial source for tool
  facts, prompts, distractors, and explanation text.
- `launch-v1.json` is the normalized compiler input. It is generated by
  `build-launch-v1.mjs` from the curated records and the accepted visual
  inventory/release ledgers.

The builder is a deterministic join and formatter. It may copy explicit
curated text, attach stable identifiers and source receipts, derive release
gates from accepted ledgers, and reject incomplete closure. It must not invent
instructional facts, prompts, distractors, rationales, or Nassau claims. Add or
change that material in the curated module first and review the resulting diff.

Run:

```sh
node content/authoring/packs/build-launch-v1.mjs
node content/authoring/packs/build-launch-v1.mjs --check
```

The content-compiler build runs `--check` and fails if the normalized JSON is
stale.

## Launch-pack closure

The pack is English-only and covers the statewide entry-level series plus its
Nassau layer. Its checked closure is:

- 65 accepted atlas tools/PPE records;
- 14 accepted comparison releases;
- 90 unique original semantic objectives: 41 use, 26 recognition-feature, 11
  ungated comparison-distinction, and 12 sourced safety-application questions;
- 18 accepted hazard scenes; and
- advertised 45/60/90 global practice lengths.

The 12 safety applications replace duplicated use prompts; no two questions
share an objective or equivalence group. Public question, option, receipt, and
session coordinates are opaque ordinals or digests. Correct-option placement
comes from the explicit `launch-v1.option-order.mjs` ledger and is not derived
from those public ordinals.

Each question has an explicit AI-agent editorial review receipt. The receipt
binds the exact review-projection digest and records passed content, security,
and accessibility outcomes. Running the builder never manufactures or updates
a review: an editorial change requires a new reviewed digest in
`launch-v1.reviews.mjs`. Claims point to exact source-line receipts; rationales
point to claims; and the compiler requires bidirectional claim/source-line
closure.

Publication-gated, Tier C, and watchlist concepts remain atlas-only. The
builder and compiler both reject their use as scored options. Practice lengths
are enabled only when a compiled profile/filter capacity can supply that many
distinct objectives; under-capacity configurations stay visibly unavailable.
A pre-answer filter membership is emitted only when every displayed option
shares it. Answer-correlated authored tags never cross the precommit boundary.

Compiled per-item precommit records preserve the complete `profileIds`
compatibility set. Their singular `profileId` is a legacy primary-profile field
and must not be used to flatten multi-profile content. Compiled question
postcommit records preserve `version`, `objectiveId`, `equivalenceGroupId`, and
`factKind`. The current authoring cut advances the pack from version 2 to
version 3 because hazard-scene postcommit artifacts now use the canonical
scene-evidence schema. Version-2 receipts and durable records remain exact
historical inputs to the one-hop released-scene decoder; version 3 does not
rewrite or reinterpret their bytes. New compilation emits only the current
scene schema.

The Nassau `AnnouncementProfileFactSheet` uses six explicit fact states:
`verified`, `not_published`, `unverified`, `conflicting`, `superseded`, and
`not_applicable`. It source-binds every applicable record and history entry and
versions its effective-dated change history. The compiler rejects
missing/out-of-profile sources, invalid conflicts, overlapping effective
intervals, multiple current facts for one exam/category pair, unordered
history, and a latest history version that does not match the fact-sheet
version.

## M4/M5 handoff boundary

This content revision does not implement M4 or M5 state flows. When those
integrations land, an active session, saved review/import projection, or print
restoration record must retain the question ID and version, pack ID and version,
profile ID and version, and profile compatibility key. Historical records must
continue resolving against the exact pinned versions; a newer profile or pack
must not silently reinterpret them.

A correction draft/submission must target the same question ID/version and
profile/content-version coordinates. Building the correction endpoint is
authorized separately, but activating user-data collection remains prohibited
until the storage, retention, triage, privacy, idempotency, rate, and abuse
contract receives explicit approval.

The M4 print/restoration projection must copy each postcommit `SourceReceipt`
without reducing it to a display label. `PrintSourceReference` receives
`id`, `sourceId`, `title`, `publisher`, `evidenceTier`, `version`,
`rightsNotes`, `locator`, `excerpt`, `language`, `verifiedOn`,
`supportedClaimIds`, optional source `scope` and `sourceLocator`, and optional
`url`. It must also carry every linked
`SupportedClaim` with `id`, `text`, `sourceLineIds`, `evidenceTier`, and
nullable `caveat`; the caveat renders adjacent to the claim/explanation. The
same packet/restoration record pins question `id`/`version`, pack
`packId`/`version`, and profile `id`/`version`/`compatibilityKey`.
